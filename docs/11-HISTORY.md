# 11 · История и грабли

Как проект собирался и на чем я спотыкался. Оставил специально — тут видно, что и почему сделано так, а не иначе.

## Как всё развивалось

1. **Исходные условия.** Принтеры стоят у меня дома (сеть `192.168.10.0/24` за роутером Routerich на OpenWrt), а сервер, на котором можно крутить бота, — у брата (`atlas`, Ubuntu, всего 3.7 ГБ RAM и строгие правила: SSH только по ключам, UFW, ничего не менять без согласования).
2. **Сеть.** Связал две сети WireGuard-туннелем: роутер подключается к серверу как клиент (AmneziaWG в режиме совместимости), на сервере в `AllowedIPs` пира добавлена моя подсеть. Принтерам на роутере прописаны статические IP по MAC.
3. **Бот.** Первая версия была одним файлом `bot.py` на ~540 строк. Потом разнес по модулям: клиенты API, хендлеры, middleware, фоновый мониторинг.
4. **Дополнительно:** расчет оставшегося времени печати, кнопки Fluidd и камеры как Telegram Web App, чат с Gemini, которому в контекст подается живая телеметрия Klipper.
5. **Деплой** в Docker на `atlas`, рядом — контейнер с sing-box (см. ниже, зачем).

На практике в итоге пользуюсь в основном уведомлениями: закончилась печать, ошибка, принтер отвалился.

## Грабли

### 1. Пути в Git Bash на Windows
`cd C:\Users\...\Принтерная` → `No such file or directory`, путь «слипся» в `C:Users...`. В Git Bash `\` — экранирование. Надо писать `/c/Users/...` или брать путь в кавычки.

### 2. scp не создает папки на сервере
```
scp: realpath /home/kovis/printernaya/: No such file
scp: upload "/home/kovis/printernaya/": path canonicalization failed
```
С OpenSSH 9.0 `scp` работает поверх SFTP и родительские каталоги сам не создает. Решение — сначала `ssh ... "mkdir -p /home/kovis/printernaya/"`.

### 3. Случайно копировал venv на сервер
`scp -r` всей папки потащил локальный `venv` — тысячи файлов под Windows, которые на Linux не нужны (Docker и так ставит зависимости). Прервал, почистил папку на сервере и стал копировать только нужное: `bot.py`, `Dockerfile`, `docker-compose.yml`, `requirements.txt`, `.env`, `src/`. Копирование стало занимать полсекунды вместо пары минут.

### 4. moonraker.conf только для чтения
В Fluidd на `moonraker.conf` висел замочек. Зашел на принтер по SSH под `root`, нашел файл (`/opt/config/moonraker.conf`) и поправил через `nano`. Позже выяснил, что правильнее класть свои настройки в `mod_data/user.moonraker.conf` — он не заблокирован.

### 5. На принтере нет systemctl
`systemctl restart moonraker` → `command not found`. У Flashforge 5M урезанная система на BusyBox без systemd. Перезапускал через Fluidd (Restart Moonraker) или `/etc/init.d/moonraker restart`.

### 6. Бот висел по 10 секунд
Если принтер выключен, `aiohttp` ждал ответа по дефолтному таймауту и кнопки не отвечали. Уменьшил таймауты в `moonraker.py`:
```python
API_TIMEOUT = aiohttp.ClientTimeout(total=3.0, connect=1.5)
```
Теперь офлайн-принтер определяется за пару секунд.

### 7. Стриминг ответа Gemini дергался
Хотел, чтобы ответ печатался постепенно, редактируя сообщение каждые 1.5 секунды. Telegram ограничивает частоту `edit_text`, интерфейс подвисал. Отказался от стриминга: бот показывает «печатает...» и присылает ответ целиком.

### 8. Gemini не работает с российского IP
На моем компе все работало, а на сервере — `400 User location is not supported for the API use`. Причем ошибка вылезала и при смене статуса принтера, потому что уведомления тогда тоже генерировались через Gemini. Что сделал:
1. Уведомления ([monitor.py](../src/services/monitor.py)) переписал на обычные шаблоны без ИИ — они должны доходить всегда.
2. Взял рабочий VLESS Reality конфиг из бэкапа Podkop на роутере и поднял рядом с ботом контейнер `3dprinter_proxy` на sing-box.
3. Запросы к Gemini пустил через него (`GEMINI_PROXY=http://proxy:1080`).
4. Адреса принтеров добавил в `NO_PROXY`, чтобы они шли напрямую через WireGuard.

Позже оказалось, что провайдер сервера режет еще и `api.telegram.org` (бот периодически падал с `ServerDisconnectedError`), так что Telegram тоже пустил через этот прокси.

### 9. E0120 после того, как принтер сам обновился
Третий принтер перестал запускаться: на экране `E0120: перезагружен, пожалуйста, скопируйте логи!`, Klipper в ошибке `pin PA8 used multiple times in config`. Разбирался по логам через Moonraker, без SSH:
- `GET /printer/objects/query?webhooks` → `state_message` с текстом ошибки Klipper;
- `GET /server/files/logs/firmwareExe.log` → лог заводского экрана.

В логе нашлось, что за два дня до этого заводская прошивка сама скачала у Flashforge обновление `5.1.9` и после перезагрузки поставила его. Новая версия при каждом старте:
1. считает `printer.base.cfg` от Forge-X «битым» (`recoverCfgFile cfg file invalid`) и подменяет заводским, где есть `[led chamber_led]` на `PA8`;
2. дописывает в `printer.cfg` свой `[led chamber_light]` на тот же `PA8`.

Два блока на одном пине — Klipper падает. Закомментированный блок прошивка не считает и при следующей загрузке добавляет новый, так что правка `printer.cfg` живет только до перезагрузки.

Вторая ошибка была моя: после правки перезапускал Klipper через `POST /printer/restart`. На Forge-X 1.4.1 после обычного `RESTART` зависает заводской экран — печать с экрана не стартовала, принтер пришлось выключать, и ошибка возвращалась. Правильно — макрос `NEW_RESTART`, он перезапускает Klipper так, что экран не отваливается.

Что в итоге:
- после каждой перезагрузки третьего принтера: закомментировать активный `[led chamber_light]` в `printer.cfg` и выполнить `NEW_RESTART`;
- постоянное решение — Forge-X 1.4.2 (в Beta 4 исправлены и дубль chamber light, и зависание экрана после `RESTART`), жду финальный релиз;
- на втором принтере уже лежал скачанный `software-5.1.9.tar.xz` — убрал его из `/opt/PROGRAM/software`, пока не установился;
- на роутере закрыл серверы обновлений через dnsmasq (`update.voxelshare.com`, `update.flashforge.com`, `update.sz3dp.com`, `update.cn.sz3dp.com`), облако Flashforge при этом работает.

### 10. Камеры в локальном Fluidd пропали после переезда на общий Fluidd
Чтобы камеры заработали в Fluidd на сервере, `stream_url` в Moonraker поменял на `/pN/webcam/?action=stream`. Настройка одна на все клиенты, и локальный Fluidd (`http://192.168.10.101`) стал искать `/p1/webcam/` на самом принтере — там такого пути нет, `404`.

Думал править nginx на принтере, а его там нет: веб отдает busybox `httpd`, камера проксируется строкой `P:/webcam/:localhost:8080/` в его `httpd.conf`. Добавил рядом `P:/p1/webcam/:localhost:8080/` — теперь один и тот же путь работает и локально, и через сервер.

Еще два момента: `kill -HUP` конфиг не перечитывает (нужен полный перезапуск `httpd`), а в SSH-сессии принтера `chroot` не в PATH — запуск по `/usr/sbin/chroot`. Пока этого не знал, на минуту оставил принтер без веб-морды.

### 11. Fluidd на сервере из моей сети отдавал 403
С ПК в сети принтеров `printer.example.com` открывался с `403`, хотя туннель работал. Роутер резолвил имя в публичный IP сервера, запрос уходил через интернет, и Caddy отбивал чужой адрес. Проверил так: с `curl --resolve printer.example.com:443:192.168.1.204` сайт отвечал `200`. Лечится записью в dnsmasq на роутере, которая отдает внутренний адрес сервера, — тогда трафик идет в туннель.
